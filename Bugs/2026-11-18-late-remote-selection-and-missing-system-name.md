# 晚到遥控器未替换离线画布与缺失系统名称占位

## 现场证据

- 环境：`offline-only` build 321，当前 Mac 已保留以前测试产生的 Chromecast 档案和选中项，本次实际连接并使用小米蓝牙遥控器。
- 用户可见结果：顶部在线设备卡显示小米蓝牙遥控器，中央按键画布仍显示 Chromecast；Chromecast 无法取得可靠 macOS 蓝牙名称时，卡片显示“系统名称未知”。小米按键功能本身正常。
- 重装 App 后已完成引导、按键映射和上次选择仍存在，属于 `UserDefaults` 中的用户配置，不是应随安装覆盖清除的临时缓存。
- build 321 的脱敏运行日志显示：启动先恢复旧 Chromecast 选择；按键页的 5 秒重连窗口结束时没有在线候选；小米约 12 秒后才完成 Ready，连接回调记录 `REMOTE MAPPING_DEFAULT ... reason=previous_remote_offline`，继续保留旧画布。

## 根因

`BridgeAppModel` 只在重连窗口到期当下执行一次在线设备 fallback。当时没有设备在线，fallback 无结果；窗口结束后，小米的晚到 Ready 又被“运行期短暂断连不切换画布”的保护分支拦住。代码没有区分“本轮从未出现过的旧离线选择”和“本轮已经在线、随后短暂断开的当前选择”。

设备卡的第二行则把缺失系统名称强制替换为本地化“系统名称未知”。这不会影响身份或连接，但给用户造成识别失败的误解；同时直接删除第二行会改变卡片高度并造成页头跳动。

## 修复

- 重连窗口结束且旧选择仍离线时，保留一次“等待第一台真实在线设备”的有界意图。后续连接事件若发现在线设备，立即按既有卡片顺序选择它，并清除该意图。
- 旧选择本轮真实连上、用户手动点击设备卡或 fallback 成功时都清除该意图；普通运行期短暂断连继续保留当前画布。
- 系统名称不可读时不渲染占位文案，无障碍标签也只包含真实可用信息；使用不可见的固定行高保持卡片三行高度。连接状态和真实电量继续显示。
- 生产设置页截图夹具把 Chromecast 保持在线但不注入系统名称，覆盖该状态。
- build 号从 321 递增到 322；不修改 Chromecast ATVV 语音、IOHID 普通按键、小米 HID 路由或用户已有映射。

## 验证

- 定向策略测试覆盖：窗口内继续等待、窗口后晚到设备 fallback、普通离线选择保持稳定、旧选择真实在线优先。
- 设置页结构回归覆盖：缺名时条件渲染、无“系统名称未知”fallback、固定空白行高。
- SwiftPM 定向设置页回归使用 `--disable-keychain`，81 项通过；其中覆盖新的晚到选择策略和缺名条件渲染。
- 用户随后要求不要再启动或替换本机正在使用的 SayAll，也不要继续执行单测类验证；因此不再运行生产截图、硬件或 App 交互，只做静态检查、构建和 DMG 来源/内嵌 commit 校验。

## 验证边界

自动化和构建不能替代真实蓝牙时序。build 322 仍需用户在两台机器分别确认：只有小米在线且晚到时设备卡与画布一致；Chromecast 机器的语音、返回/静音映射和电量没有回归；双设备同时在线时手动选择不会被连接事件抢走。中英文、浅色/深色的生产界面截图本轮未执行。
